## 一、用户口述的权威设定

1. **泡泡该被打掉，不该靠走位躲。** 泡泡是能被高攻速或大范围武器打破的，
   所以"左右闪躲"本身就是遗留状态机的缺陷。此前的清泡武器切换**方向是对的**
   （想让武器承担清泡），但实现把它做成了整段不开火，见
   `docs/fishron-threat-identities.md`。
2. **审核路线清单**（只有这些配装允许用于对应 Boss；小模型若启用也只能用这些）：
   - 猪鲨：① 蛙靴 + 仙灵翅膀及同级翅膀 + 可靠冲刺来源（克苏鲁之盾／忍者大师套装／
     水晶刺客套装）；② 史莱姆女士鞍；③ 可靠的疾旋鼬／桃旋鼬；
     ④ 蛙靴 + 猪鲨翅膀及同级强力翅膀 + 可靠闪避来源。
   - 光之女皇：① 蛙靴 + 猪鲨翅膀及同级强力翅膀 + 冲刺；② 扫帚飞行坐骑；
     ③ 雨天时的虾松露坐骑。
3. **小模型是最终手段，不是首选**：只有固定状态机被证明无法取胜时才考虑，
   按"每个 Boss × 每种配装"训练，且只允许走上面的审核路线。资源开销过大。
4. **测试精简是次要目标**：当前近 750 个用例是先前 Agent 的遗留膨胀，
   欢迎清理，但不要因此耽误战斗闭环。
5. 参考打法教学（用户提供）：
   - 猪鲨 https://www.bilibili.com/video/BV1XVwnerECt/
   - 光之女皇 https://www.bilibili.com/video/BV1YqQ2YRE6F

## 三、本轮被数据证伪的两个假设（不要再试）

1. **跑道左边界不可达，是承重的。** 原生 `Player.BordersMovement` 写死 `num = 640`，
   把 `position.X` 夹到 `leftWorld + 640` 并清零该轴速度——所以 `_bandLeft =
   worldLeft + 260` 在真游戏里也不可达（夹具物块扫描 `outside=0` 证明 x=640 是原生保底，
   不是夹具几何）。但把边界推到原生边界后：tick 670–730 的泡伤整簇消失（改前 9/9，
   改后 0/6），**六条种子全败**，全部死于跑道尽头的龙卷风。
   → 代码里在 `_bandLeft` 处留了"别再修"的注释。
2. **冲刺的逃逸侧必须每帧重算，不能锁定。** `_chargeHorizontal`（`4c307ad` 的顺手改动，
   随清泡武器一起被回滚，从未单独量过）补测后十条只有 1 胜、受击 78。
   → 判据：**被事件穿过的量该锁（贴身、悬停窗口），被持续跟踪的量不该锁（冲刺瞄准）**。
   注意 `docs/tutorial-pattern-notes-20260913.md` 里"latching the charge escape direction
   for the group"这句已被证伪，该文件已改正。

`bubble-line` 的 39% 按用户口述就是缺陷本身（Boss 在吐泡期间绕圈，逐帧"远离 Boss"
让玩家原地左右摇）。本轮删掉了这个逐帧推导，并把只服务于它的
`AwayFromBoss` / `Split` / `DominantAxisFraction` 一并删除（脚本 -50/+11 行）。

但"删掉闪躲"之后**替代动作用什么**，两次测量都给出否定答案：

| 替代动作 | 胜 | 受击 |
|---|---|---|
| 守住跑道方向 `_patrol`（直线行进） | 3/10 | 83 |
| 站定开火 `horizontal = 0` | **0/10** | 83 |
| （保留原逐帧闪躲 = 当前主线） | 4/10 | 75 |

两者受击都涨到 83。所以结论必须诚实地分成两半：

- **用户的规则针对的是武器，不是走位。** "泡泡该被打掉"这一半已经生效——
  回滚清泡武器切换后泡泡阶段**不再整段不开火**，这才是那半句话要修的东西。
- **逐帧横向闪躲虽然动机是错的，但它承重。** 泡泡会跟踪玩家，直线行进等于把整条
  泡泡线拖走；站定更差，被 Boss 绕圈的轨迹把泡泡送上来。在找到**已测量**的替代动作
  之前，这段闪躲不能动。删掉它换来的不是"不再怕泡泡"，而是多挨约 8 次。

**教训**：用户否掉的是"闪躲的动机"，不等于"必须换成一个方向走"，也不等于"不动"。
在泡泡会跟踪玩家的机制下，"不动""乱走""直线走"是三件不同的事，必须分别测。

## 七、光女受击的性质和猪鲨完全不同（下一次要动的就是这里）

猪鲨的受击是**离散事件**（一次一个泡、一次一次冲撞），光女的受击是**持续多段流**。
逐帧受击清单里的实际形态：

- 扫帚（`rt-eb2`/`rt-eb3`）：`src=923` 在 `flight-sun-dance-pivot` 相位里**连续命中了约 185 个 tick
  （t865–t1050 不间断）**，同一 tick 常有 2–5 段；`src=873` 在 `prismatic-bolts` 与
  `dash-perpendicular` 里也是同一 tick 叠好几段；另有本体的 `src=636 npc` 接触。
- 虾松露（`rt-er2`）：同一形态——`873` 成片、`636` 本体接触、`872` 在
  `inter-attack-reposition` 成片。

也就是说：**光女脚本不是"闪避失败一次"，而是有几个相位整个泡在伤害里**。
`flight-sun-dance-pivot` 这个名字说明"贴着旋转轴躲"这条教程规则**已经写进代码了**
（`EmpressStrategy` 的 state 6 → 朝本体线做垂直移动），但实测仍在这个相位里连吃 185 tick，
所以问题不在"没实现"，而在**实现出来之后仍然站在光束里**——这正是本轮在猪鲨侧验证过的
那类问题：计划字段写了，不等于动作发生了（见 `docs/fishron-threat-identities.md`）。

**下一步顺序（下一轮从这里开始）**：

1. 先量光女脚本在 `sun-dance` 相位实际上是否产生了"朝本体线"的垂直输入，
   以及玩家相对旋转轴的位置——用与"泡泡黑障"同样的手法：计划值 vs 回放后的实际值。
2. 再动 `broom` / `rain-fishron` 的驾驶闭环（它们 1900 tick 就结束，连输出时间都不够）。
3. 猪鲨侧若要扩充可验收路线，第一顺位是史莱姆女士鞍（见第六节）。

## 八、第 1 项已量完：**那条"贴着旋转轴"的规则根本不在公式脚本里**

`tutorial-pattern-notes-20260913.md` 写着"state 6 (Sun Dance) 不再使用切线绕行，
改为朝本体线做垂直移动"。**这句话描述的是 `BossStrategyCatalog.cs` 里的旧评分器，
而这三条光女路线实际跑的是 `EmpressFlightScript`／`EmpressWingScript`。**
公式脚本里 state 6 调用的仍是 `Tangent()`：

```csharp
horizontal = input.PlayerBelowBoss ? -loop : loop;
vertical   = input.PlayerRightOfBoss ? -loop : loop;
```

这是**按象限取的固定斜向输入，不是绕行**。`rt-eb1` 的实测（boss 在右上、玩家在左下）：

| 805 | 325 | 朝本体 |
| 900 | 101 | 朝本体 |

也就是说这个相位**先穿过本体、再一路飞出武器射程**，与相位名 `sun-dance-pivot`

## 九、顺带验证掉的一个错误假设：光女不是"治疗黑障"

一开始看到 `life` 从 512 单调掉到 0、最大值只有 529，很像是"请求了治疗但没生效"
（和清泡武器同类）。逐项查证后**不成立**：

- 夹具确实发了治疗药水（`GameProbe.cs` L1798–1802，`inventory[10]` = 15 瓶 ×20）。
- 计划值也确实落地了：采样帧里 `plan.quickHeal=true` 51 帧，其中
  `actualAtApplyReturn.controlQuickHeal=true` **30 帧**——和猪鲨胜局（82 → 37）同量级。

真实原因是**消耗战**：最大生命约 512–529，单次受击约 45，**约 12 次受击必死**，
而治疗药水有 60 秒冷却，一场 1900 tick（约 32 秒）最多喝一次。
所以光女的约束就是**受击次数**，不是治疗：要能打就必须把受击压到 6 次上下。

死亡相位并不集中（`inter-attack-reposition` 里 90 tick 吃 335 段 `873`、
`prismatic-bolts`、`dash-perpendicular`、`ethereal-lances` 都有），
说明**光女需要的是一次回路重做，而不是再调一个相位**。这是下一轮的主要工作。

## 十、全字段"计划 vs 落地"审计：猪鲨的管道已经干净了

"计划字段写了不等于动作发生了"这一类缺陷已经连续咬过两次（清泡武器整段不开火、
`SetSelectedItem` 缺失），所以这次不再一个个猜，而是**把计划里每个字段都拿出来对**
（36 条运行：`rt-lu*`／`rt-bl*`／`rt-st*`／`rt-cl*`，判据是 `plan` 对
`actualAtApplyReturn`）：

| 计划字段 | 计划为真 | 落地为真 | 丢失 |
|---|---|---|---|
| `horizontal` → `controlLeft/Right` | 7415 | 7415 | **0** |
| `jump` → `controlJump` | 2878 | 2878 | **0** |
| `dash` → `controlDash` | 480 | 480 | **0** |
| `fire` → `controlUseItem` | 6915 | 5927 | 988 |
| `quickHeal` → `controlQuickHeal` | 2071 | 1046 | 1025 |
| `hook` / `quickMana` / `toggleMount` | 0 | 0 | 0（翼类路线本就不用） |

那 988 帧"声称开火却没开火"看起来很像黑障，于是按三层往下挖：

1. **按相位分组**：没有任何相位是黑障。丢失率在所有相位都是 13–22%，
   `*-dash` 相位反而只有 2–5%。
2. **按槽位匹配分组**（复现泡泡黑障的判据）：`plan.preferredWeaponSlot` 与
   `selectedItem` **不一致的帧数为 0**——所以这次不是槽位机制。
3. **按武器占用分组**：988 帧里有 **974 帧 `usingOrReusingItem=true`**，
   即武器正在挥动/后摇，不开火是正常的。真正无法解释的只剩 **14 帧（0.2%）**。

`quickHeal` 那 50% 也不是黑障：胜局里生命值确实在 161↔442 之间来回（治疗生效）。
两者的丢失都是节流（药水冷却／资源闸门），不是"计划没落地"。

**结论**：猪鲨公式路线的**管道层已经查干净了**——所有方向/跳跃/冲刺字段 100% 落地，
开火只剩 0.2% 无法解释。这意味着猪鲨剩下的受击**不再是接线问题，而是行为与几何问题**，
下一轮不该再往"计划 vs 落地"方向找。

**泡泡合计 43/75 = 57%**，是压倒性的第一来源——这与用户那条规则完全一致
（"泡泡是可以被高攻速或者较大范围的武器打破的"）。但我们已经验证过开火覆盖率达 99.8%，
所以问题不是"没开枪"，而是**枪口指向哪里**。

按相位统计 `plan.aim` 与"玩家→猪鲨"方向的夹角（十条种子）：

| 相位 | 采样帧 | 中位夹角 | 夹角 ≤15° |
|---|---|---|---|
| `bubble-line`（吐泡） | 152 | **0.0°** | **100%** |
| `personal-space` | 141 | 0.0° | 100% |
| `tornado-clear` | 183 | 0.0° | 100% |

| `precharge-jump` | 529 | 0.0° | 99% |

也就是说：**在造成 57% 伤害的吐泡阶段里，武器 100% 的帧都瞄准猪鲨本体，从未瞄准过泡泡。**
泡泡是追踪型、接触即爆，于是它们一路贴到玩家身上——正好解释了
"打了 99.8% 的帧，泡泡伤害却占 57%"。

代码侧的机制已经定位（`CombatPlanner.cs`）：

```csharp
private static float TargetScore(TargetSnapshot target, Vec2 player)
{
    var score = Vec2.DistanceSquared(target.Center, player);
    if (target.Boss) score -= 1000000f;      // ← Boss 获得 1e6 的固定优势
    ...
}
```

`-1000000` 压倒一切距离项，所以目标永远是 Boss，`plan.AimWorld` 也就永远
是 `target.Center`（或它的预测拦截点）。**没有一个分支会让泡泡成为瞄准目标。**

**下一步（下一轮第一件事）**：在吐泡相位（原生状态 2/7）里让"逼近到危险距离内的爆裂泡泡"
成为瞄准候选——即目标选择要有一条"威胁优先于 Boss"的通道，而不是只靠 `TargetScore`。
动手前必须先确认一件事：**泡泡是否已经出现在规划器的目标列表里**
（探针观测的 `npcs` 有数量上限与两级优先，需先查 `omittedNpcs`，
不要把它当成"规划器看不到泡泡"的证据；规划器的快照由插件构建，与探针观测上限无关）。

## 十五、于是约束被量化了：胜负只由"受击速率 vs 击杀耗时"决定

把三件事放在一起：

- 获胜局与失败局的**伤害率完全相同**：都是 78000 / 约 4800 tick ≈ **16.25 伤害/tick**（≈975 DPS）。
- 击杀窗口固定：78000 ÷ 16.25 ≈ **4800 tick**。
- 实测受击速率约 **每 450–500 tick 一次**，每次约 45–60 伤害 ⇒ 约 10 次受击致死。

**所以胜局不是"打得更狠"，而是"挨得更慢"**——败局在 3100–4600 tick 就被打死，
此时 Boss 还剩 16k–34k 血（即已打掉 83%）。要在 4800 tick 的击杀窗口里活下来，
必须把受击速率**大约减半**（从 ~1/470 降到 ~1/950）。

这条结论同时关闭了两个方向：**输出不是杠杆**（已经开火 92%），
**环与刷新不是杠杆**（存活期全程在线）。剩下的唯一杠杆就是受击速率，
而这需要一次性砍掉近一半——这已不是"再调一个相位"能办到的量级，
与第十三节"瞄准清泡被否"合起来看，是针对同一堵墙的第三次撞墙。

**因此下一轮的优先级改为路线层面的测量，而不是继续调回路**：
`fishron-queen-slime` 目前只有 3 条种子的 1/3，是全项目唯一一个数值上可能优于
仙灵翼路线的候选。先用 20 条种子把它量准——如果它同样停在 50%，
那么"固定状态机无法在没有输出/载具变更的前提下达到 90%"就是一个有证据的结论，
届时应把这一点如实上报，而不是继续消耗轮次做微调。

## 十七、几何缺陷（左墙卡死）确实存在，但"修掉它"被 0/20 否掉

先看新证据——**玩家被原生左墙卡死的那些帧特别危险**：

| | 帧数 | 占比 | 60 tick 内受击的比例 |
|---|---|---|---|
| 卡死在 x≤641 | 136 | **6.1%** | **22.1%** |
| 自由移动 | 2076 | 93.9% | 9.2% |

即卡死帧的危险度是其余帧的 **2.4 倍**，而它只占 6% 的时间。机制也清楚：
`_bandLeft = worldLeft + 260 = 276`，但 `Player.BordersMovement` 把玩家钳在
`Main.leftWorld + 640 = 640`，所以**左边界永远到不了**，`ApplyArena` 里
`if (x <= _bandLeft && horizontal < 0) horizontal = 1;` **这一支在实战中是死代码**——
玩家顶着 `horizontal = -1` 的命令被墙按住，直到脚本自己换相位才离开。

于是把左回转点移到可达区域内（`clamp + 260 = 884`，玩家**完全不碰墙**）再测：

| | 胜/总 | 受击速率 | 存活时长 |
|---|---|---|---|
| 基线（同 20 种子） | **10/20** | 约 1/470 tick | 4000–4600 tick |
| 左回转点内移 | **0/20** | 约 **1/380 tick** | 2800–3900 tick |

**0/20，彻底失败且方向相反**——受击速率不降反升，存活时间反而更短
（`rt-lbf1..20`，构建 `94230206DE03B193`，已回滚，Core 回到 `7123AAE7`）。

结论很重要：**那个 2.4 倍是相关，不是因果。** 卡死帧之所以危险，是因为
"回路正好在那里保持站位"的那个时刻本来就处在危险窗口里；把站位拿掉并不会消掉危险，
反而**打乱了 W 循环与 Boss 攻击时钟的同步**——这与代码里早就记下的那条
"移到边界后每个种子都死在跑道尽头的克苏鲁龙卷"是同一个机制。
现在这个"拿掉左墙站位"的方向已经在**两个不同的内移量**（0 和 +260）上各测一次
（0/6 与 0/20），整个家族可以关闭了；我把这段结论直接写进了
`FishronWingScript` 的注释里，避免以后第三次重试。

**下一轮的方向因此变成**：不要移除站位，而是**保留站位的时长、只改变站位的质量**——
即让这段"等时钟"的时间发生在离墙有空间的地方（可以在那里闪避），
同时保持 W 循环的时序不变。这是唯一还没被否掉、且与"时序是硬约束"这条新结论一致的改法。

## 十八、受击的"原生状态 × 来源"交叉表：伤害是弥散的，没有单一元凶

之前一直用**脚本相位**给受击归类，但那不是 Boss 真正在做什么。这次直接读原生
`npc.ai[0]`（猪鲨 AI_069 的状态），交叉来源类型，得到 75 次受击的真实结构
（`ai[0]` 与相位的对应也一并验证：0/5=悬停、1/6=冲刺、2/7=吐泡、3/8=鲨鱼龙）：

| 原生状态 | 来源 | 次数 |
|---|---|---|
| bubble | npc/371 泡泡 | 15 |
| charge | npc/370 本体 | 11 |
| hover / hover2 | npc/371+372+373 泡泡 | **19** |
| hover / hover2 | npc/370 本体 | **10** |
| sharknado2 | npc/373 | 4 |
| charge2 / st10 / sharknado2 | projectile/386 龙卷 | 6 |
| 其余 | — | 10 |

按攻击类型汇总：**悬停期 32 次（43%）、冲刺期 17 次、吐泡期 16 次、鲨鱼龙期 5 次。**
按来源汇总仍是泡泡 43 / 本体 25。

两个要点：

1. **泡泡不止在吐泡期命中**——吐泡期 16 次，**悬停期还有 19 次**。也就是说泡泡是
   吐泡阶段发射、在之后的悬停阶段才追到玩家的。这解释了为什么"瞄准泡泡"能打掉泡泡
   却不减少受击：真正的窗口在悬停期，而那时泡泡已经在身后了。
2. **受击是弥散的**：最大的单一格子只占 15/75（20%）。不存在"修掉这一个就翻盘"的缺陷，
   这也解释了为什么前七轮里每一个看起来必然有效的定点修改最后都只是持平或更差。

## 十九、本体接触的量化，以及"提早逃离"实测无效（8/20 对 10/20）

把 25 次本体（370）受击的中心距全部量出来：

```
112, 114, 124, 125, 125, 125, 144
```

**全部 ≤144 px，而脚本的 `PersonalSpace` 触发半径是 200 px**——也就是说这 25 次里，
逃离分支**每一次都已经在触发状态**，只是触发得太晚，没能把玩家带出本体的接触包络。
于是把触发半径从 200 放宽到 **320**（提早约 120 px、约 7 tick 开始逃离）并测 20 种子：

| | 胜/总 | 配对 |
|---|---|---|
| 基线 | **10/20** | |
| `PersonalSpace = 320` | **8/20** | 基线胜→负 6 个，负→胜 4 个（McNemar p≈0.75） |

**持平偏负，无收益，已回滚**（`rt-ps31..20`）。这条否定的信息量在于：
**"更早开始逃离"不是问题所在**——既然 200 就已经在触发，而 320 也没有帮助，
那么冲刺期的本体命中就不是"启动太晚"，而是注释里早就写明的那件事：
**玩家速度（6.2 px/tick）本来就追不上猪鲨（8.5 px/tick），冲刺一旦发起，接触就基本注定。**
能改的只有"垂直于冲刺方向"的分量，而那不是靠加大半径能解决的。

**截至本轮累计**：七轮里被测量支持的改动只有一项（贴身侧向锁定，3→4 胜），
其余五项（泡泡阶段保持巡逻、泡泡阶段横移归零、瞄准清泡、左墙站位、放宽贴身半径）
都被实测否掉。最优路线仍是 `fishron-fairy-wing` 的 **19/40 = 47.5%（下界 32.9%）**。
结合第十八节的"弥散"结论，现在可以比较有把握地说：**固定状态机缺少的不是某一个缺陷，
而是"在悬停期重新处理身后残留泡泡"这一整套能力**——这也正是用户所说
"泡泡可以被打破"的那部分，而它需要的是新的决策层，而不是再调一个常数。

## 二十、光女侧：把"太阳舞枢轴"改成真正的环绕，实测大幅变差（伤害 −45%）

第八轮起转向光女（目标里有一半是它，而前七轮全在猪鲨上）。先修 §8 记录的那个
"实现级缺陷"：`EmpressFlightScript` 的原生状态 6（太阳舞，相位名 `sun-dance-pivot`）
调用 `Tangent()`，它只按玩家所在象限选一条**固定对角线**并保持整个状态：

```csharp
horizontal = input.PlayerBelowBoss ? -loop : loop;
vertical   = input.PlayerRightOfBoss ? -loop : loop;
```

我把它换成真正保持距离的环绕（`Pivot`：半径 360 px 以内沿半径向外、以外走切线
`(-dy, dx)·loop`）。20 条配对种子（seed 1–20）：

|---|---|---|---|---|
| 基线 `7123AAE3` | 0/20 | **2857 tick** | 13.2 | **523,523** |
| 环绕枢轴 `7B4EE01E` | 0/20 | **1834 tick** | 10.6 | **286,980** |

**伤害直接砍掉 45%，存活时间缩短 35%，已回滚。** 方向很清楚：
固定对角线之所以"更好"，是因为它把玩家**送远到约 3000 px**，而太阳舞的光束场在光女附近最密；
我的环绕把玩家留在 360 px，等于**泡在光束里**。也就是说，§8 当时的诊断

但那段行为里真正救命的是"随后飞远"，而我只修掉了前者、毁掉了后者。

## 二十一、一次差点得出完全错误结论的流程事故（必须记住的教训）

第一次取基线时我用 `git stash` 存起源码、直接跑 wave（tag `eb0`，20 条种子，全部 0 胜、
平均 1834 tick）。随后应用改动再跑（tag `eb1`），结果**每一条种子的 ticks / hits / bossLife /
damage 都与"基线"逐位相同**。按本项目的判定规则，这本该读成
"被改的分支根本没有执行"——而实际上状态 6 在运行里出现了 13 次。

真相是 `probe-manifest.json` 里的 `InputCoreSha256`：**两次 wave 都是 `7B4EE01E`（改后的构建）**。
原因：**`git stash` 只改源码，不会让已经编译好的 DLL 失效**，而探针用的是磁盘上那份旧 DLL。
于是那个"基线"根本不存在，而"逐位相同"是同一个构建跑了两次的必然结果。
只有 `ebz`（先 `git checkout` **并重新 build**、确认哈希为 `7123AAE3`）才是真基线，
也正是它立刻显示出巨大差异。

**规则（今后每次测量都要执行）**：两组 wave 的 `probe-manifest.json → InputCoreSha256`
必须不同，否则比较无效；`git stash` / `git checkout` 之后**必须重新 build**。
另外 `eb1` 那条 wave 以 exit 1 结束，因为我在它还在跑的时候重新编译了 Core——
正是"wave 运行期间不要改动/编译"那条既有禁忌，已再次验证。

**顺带记下光女的真实现状**：`empress-broom`（夜间）20 条种子 **0 胜**，
平均存活 2857 tick、受击 13.2 次、只打掉约 34% 血量。
受击速率约 1/216 tick（猪鲨是 1/470），伤害率却更低——**光女这条路线比猪鲨差得多，
问题不在枢轴细节，而在"为什么 1900–2600 tick 内就吃满 13 次"**。

## 二十二、【保留】找到光女的支配变量：距离，收益 +119%

第九轮继续查光女。先把受击流拆开（20 条基线运行，共 12631 条伤害记录）：

按原生状态：**state 6（太阳舞）4458 = 35%**，state 1 = 22%，state 2 = 15%，state 8 = 15%。
也就是说伤害同样**弥散**，但最大的单块仍是太阳舞。

然后做了一个之前从没做过的测量——**把"距离"当作自变量**，统计每个采样帧之后 30 tick 内
是否吃到伤害：

| 玩家—光女距离 | 帧数 | 30 tick 内受伤的比例 |
|---|---|---|
| 0–150 px | 121 | **74.4%** |

上一轮"环绕 360 px"为什么惨败（正好停在 26% 那一档）；固定对角线为什么反而好
（它把玩家送到 3000 px，即 0.5% 那一档）；以及太阳舞为什么占 35%
（那时正是玩家被送到近处的窗口）。

而 `EmpressFlightScript` 的默认分支 `OrbitQuadrant`（45 tick 换一个象限）**本质上就是
绕圈，把玩家钉在 150–500 px，也就是 26–38% 那一档**——形状本身就选错了。
于是加了一道闸门（`StandoffRadius = 900`）：距离小于 900 px 时**只沿半径往外飞**，
超过 900 px 才恢复原有的象限循环（这样也不会一路飞出场地）。

20 条配对种子（**哈希已验证：`ebz` 全为 `7123AAE3`、`eb3` 全为 `9B85A4A3`**）：

|---|---|---|---|---|---|
| 基线 | 660,522 | 2857 tick | 13.2 | 1/216 | 约 34% |
| 距离闸门 | **1,444,319（+119%）** | **5702 tick** | 14.75 | **1/387（−44%）** | **约 74%** |

**20 条种子的伤害全部提高。** 最好的一条（seed20）把光女打到只剩 **4714 血**（95%），
seed3 剩 6150（94%）、seed1 剩 7060（93%）。

这是九轮以来**第二个被保留的改动，也是第一个大幅度的改动**。要注意它并没有减少
*绝对*受击次数（13.2 → 14.75），而是把存活时间翻倍、受击速率砍掉 44%——
现在的差距从"打掉 34% 就死"变成"**只差 1–3 次受击就能收掉**"。
下一轮的目标因此非常具体：**把残余的那 1–3 次受击去掉**，其中最大的一块仍是
太阳舞（35%），而太阳舞期间目前用的还是那条固定对角线。

## 二十四、"两条曲线的交点"看起来是个最优点，但被否掉（−7.8%）

`eb4` 运行里补测了**输出随距离的变化**（相邻采样帧的 Boss 掉血 / 时间）：

| 距离 | 伤害/tick（输出） | 受伤率（来自 §22） |
|---|---|---|
| 0–300 | 13.74 | — |
| 300–500 | **16.99** | 26.2% |
| 500–700 | **16.79** | — |
| 700–900 | 13.86 | — |
| 900–1300 | **11.99** | 0.5% |
| 1300+ | 7.32 | 0.5% |
| 500–800 | — | 6.0% |

当时的推理是：`StandoffRadius = 900` 只看了防御曲线，而 900 处输出已经从峰值掉到
11.99；**500–700 处输出 16.79、受伤率只有 6%**，所以把半径从 900 下移到 650
应该能换来约 +40% 输出。实测 20 条配对种子（哈希已验证：`eb4` 全 `E910FAEF`、
`eb5` 全 `19CA3F98`）：

| | 总伤害 | 平均受击 | 平均存活 |
|---|---|---|---|
| `eb4` 半径 900 | **1,499,744** | 13.75 | 5639 tick |
| `eb5` 半径 650 | 1,382,351（**−7.8%**） | 14.35（+4%） | 5228 tick |

**更差，已回滚**（`git checkout` 回到已提交的 900）。

**原因（这一条要记住）**：**"输出随距离"这条曲线不是因果的**——它是在不同状态上
汇总出来的相关性，而各个距离区间是被**不同状态**占据的（近距离区间主要出现在冲刺/弹幕
状态里）。曲线自己就暴露了这一点：**0–300 的输出（13.74）反而比 300–500（16.99）低**；
如果距离本身能提高输出，越近应该越高，而不是先升后降——近距离那一段的低输出其实是
**被打断**（受击硬直/击退）的代价，不是距离的功劳。相比之下防御曲线是**每帧的危险率**，
更接近因果，而且它单调到 800+ 从未反转。

所以"移到输出峰值去"这个动作，把一个**被状态混淆的相关性**当成了杠杆。
**当前最优仍是半径 900 + 太阳舞闸门（`E910FAEF`）：20 条种子 1,499,744 总伤害、
最好几条打到 91–93%。** 距离这条路至此已经试到边界，
下一轮必须换成**按状态/图案**的决策（太阳舞占残余伤害 58%），而不是继续调半径。

## 二十五、【保留】太阳舞的躲避找到了：**不要停在她的垂直轴上**（首胜）

把太阳舞的每一帧按"玩家相对光女的位置"分桶，统计 30 tick 内的受伤率：

| 相对位置 | 帧数 | 受伤率 |
|---|---|---|
| 正下方 / **居中**（│dx│≤150） | 33 | **100%** |
| 很远下方 / **居中** | 36 | **97.2%** |
| 很远下方 / 右 | 266 | 18.8% |
| 很远下方 / 左 | 98 | 13.3% |
| 下方 / 右 | 65 | **4.6%** |

**信号极强**：停在她垂直轴 150 px 以内，受伤率 97–100%；**一旦横向拉开，立刻降到 4.6–18.8%**。
这正是"距离"解释不了的那 58%：玩家不是太近，而是**正对着光束柱**。
而 `Standoff` 在玩家位于正下方时（dx 落在死区内）**只发垂直指令**，等于把她正下方那条
死亡走廊当成了安全区。

于是给太阳舞加了一条**横向净空**规则：│dx│ < 200 px 时强制横向输入（朝玩家已有的那一侧，
若正好为 0 则用 `_loopDirection`）。20 条配对种子（哈希已验证：`eb4` 全 `E910FAEF`、
`eb6` 全 `82683094`）：

| | 总伤害 | 平均受击 | 平均存活 | 胜 |
|---|---|---|---|---|
| `eb4` 仅距离闸门 | 1,499,744 | 13.75 | 5640 tick | 0 |
| `eb6` 加横向净空 | **1,584,802（+5.7%）** | 14.20 | 5858 tick | **1** |

**逐种子配对：14 好、2 差、4 平**（符号检验 p≈0.002），
并且拿下**光女路线的第一场胜利**（seed11：6934 tick、13 次受击、98,000 打满）。
仅次于它的败局：seed9 打到 92,120（94%）、seed17 90,837、seed5 90,281。

**保留。** 需要说清的是：1/20 胜仍然只是 5%（Wilson 区间 [0.1%, 26%]），
距离 90% 下界还差得远；这条改动的意义在于**它第一次让胜局出现**，
而且机制是被量化的（100% → 4.6% 的分档），不是碰运气。
下一轮应先把太阳舞这条线补到 40 条种子确认，再用同样的"按状态分桶找几何规律"的方法
去处理 state 1（15.6%）与 state 2（10%）。

## 二十六、【保留】state 1 的危险方向是"下方"而不是"近处"（+8.7% 伤害）

对 state 1（攻击间重新定位，残余伤害 15.6%，全部来自 873）做同样的几何分桶：

| 相对位置 / 距离 | 帧数 | 受伤率 |
|---|---|---|
| 下方 / 居中 / <400 | 257 | 20.6% |
| 很远下方 / 右 / 400–900 | 133 | **32.3%** |
| 下方 / 右 / 400–900 | 35 | 25.7% |
| **水平 / 右 / <400** | 88 | **0.0%** |
| **水平 / 左 / <400** | 85 | **1.2%** |
| 上方族 / >900 | 133 | **0.0%** |

危险的是**下方**，不是近处——水平同高、400 px 以内反而 173 帧只有 0–1.2%。
而 `Standoff` 从下方出发的径向后撤会**把玩家推得更深**，正好推进 20–32% 那一带。
于是 state 1 反转垂直分量：玩家低于她超过 100 px 时改为**爬升到同一水平**

（1/20 的 Wilson 区间是 [0.1%, 26%]），而"最好三条"整体上移
（第 2、3 名从 92120/90837 提到 95162/93104），所以按聚合证据保留。
**下一轮的首要任务就是把 `eb7` 补到 40 条种子**，用同一个口径和 `eb6` 对比——

## 二十七、当前最优构建的 32 条种子实测：3.13%，整个分布挤在击杀线下方

扩样时**后台 wave 在 seed 33 被中断**（与等待它的那次调用一起被杀）：
计划 40 条，实际完成 **12 条（seed 21–32）**，全部哈希 `F0E80769`（构建正确）；
未完成的 seed 33 目录**按规矩保留、不删**。这是本项目**第二次**出现"长 wave 随中断一起死"
（第一次见 §21），所以此后单次 wave 一律不超过 20 条，宁可多跑几次。

把 `eb7`（seed 1–20）与 `eb7b`（seed 21–32）合并——**同一构建 `F0E80769`、
同一场景/路线（`empress-night` / `empress-broom`）**：

| 指标 | 值 |
|---|---|
| 种子数 | 32 |
| 胜 | **1**（seed 29） |
| 胜率 | **3.13%** |
| Wilson 95% 下界 | **0.55%** |
| Wilson 95% 上界 | 15.74% |
| 平均伤害 | 87,732 = **她的 89.5%** |
| ≥90k 的种子 | 14 |
| ≥95k 的种子 | 4 |
| <60k 的种子 | **0** |
| 平均受击 / 存活 | 14.03 / 6362 tick |

**这张表说明了当前瓶颈的形状**：32 条里**没有一条低于 60k**，平均已经打到 **89.5%**，
14 条超过 90k——**整个分布挤在击杀线下方一点**。所以问题不再是"打得不够多"或"活不下来"，
而是**最后约 10% 加上 1–2 次受击**。这也解释了上一轮"胜场 1→0"为什么不值得当真：
整个分布离 98k 只有一步之遥，单条种子的胜/负在 n=20 上就是硬币。

**验收差距要说清**：下界 0.55% 对要求的 90%，差两个数量级。
但相对起点（20 条 0 胜、只打掉 34%）已经是质变：
**距离曲线（+119%）→ 太阳舞横向净空（首胜）→ state 1 反转垂直（+8.7%）**，
三步把这个路线从"必死"推到了"平均 89.5%"。

**顺带记两个把我自己坑过的统计坑**（PowerShell 5.1，都直接影响验收数字）：
`(单个对象).Count` 返回 `$null`（本轮因此一度把 1 胜算成 0 胜）；
`[math]::Max(0, $double)` 会命中 `int` 重载**把小数截成 0**（因此第一次算出的 Wilson 是 [0%, 0%]）。
以后一律用 `@(...).Count` 与显式 `[double]` 转换。
